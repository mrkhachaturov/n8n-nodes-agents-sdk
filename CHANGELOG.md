## 0.3.0 — 2026-04-18

### Added

- Microsoft Agent 365 support via new `M365Agent365Api` credential type.
- Top-level `Authentication Kind` parameter on `M365AgentTrigger` and `M365Agent`
  (`classicBot` | `agent365`) — gates which credential is required.
- Per-outbound-operation `Identity Mode` on Message and Card ops when
  `authKind=agent365`: `autonomous` and `agentUser` (sidecar-only).
- Shared auth router (`shared/auth/router.ts`) routing token acquisition to
  three backends: classicBot (unchanged), agent365 inline (direct MSAL wrapper),
  agent365 sidecar (HTTP to the `mcr.microsoft.com/entra-sdk/auth-sidecar`
  container).
- Inbound JWT validation routing — inline multi-issuer or sidecar `/Validate`,
  configurable per credential.
- Sidecar deployment artifacts in the repo: `examples/sidecar/` with dev and
  swarm docker-compose variants. Not bundled in the npm tarball.
- Guides: `docs/auth-guide.md`, `docs/obo-guide.md`, `docs/licensing-notes.md`.

### Changed

- `M365AgentApi` credential is unchanged from 0.2.1 — zero migration for
  existing classic bot credentials.
- Envelope gains an optional `authContext` field when `authKind=agent365`,
  carrying the inbound bearer and validated claims for downstream delegated
  (OBO) flows.

### Notes

- `Interactive/OBO` identity mode is implemented in the shared auth router
  but not surfaced on the Message or Card operation UIs. The Bot Connector
  API accepts only application-permission tokens, so OBO tokens have no valid
  audience there. OBO will be exposed once Graph / MCP operation resources
  are added to `M365Agent`.
- `Invoke Response: respond` is unchanged — it writes to the open webhook
  connection and does not acquire an outbound token.
- Zero behavior drift for classic bot users — regression tests guard
  byte-identical outbound HTTP.

#### 0.2.1

**New**

- `M365 Agent` gains a `Card / Update` operation — re-renders an Adaptive Card in place by calling the Bot Connector's `updateActivity` with a new template expansion. Mirrors `Card / Send` (same Card Template + Binding Data + Fallback Text fields) but requires `activityId` on the conversation reference (the card to update). Closes the gap where state-changing Adaptive Card flows (e.g. status transitions with `Action.Submit`) had to chain a card build + raw HTTP call to update the original message.

Per manifest §6.1, `send` and `update` are variants of the same user intent on the `Card` resource — they live on one node, not two.

#### 0.2.0 — UX realignment (BREAKING)

The three separate action/builder nodes (`M365SendActivity`, `M365TextMessage`, `M365CardTemplate`) collapse into a single `M365 Agent` node using n8n-native resource/operation UX. Workflows saved against 0.1.x will not auto-migrate — they must be rebuilt on the new node shape.

**New**

- `M365 Agent` action node with resources `Message` / `Card` / `Invoke Response` and per-resource operations. Canvas subtitle shows `operation: resource`.
- `Conversation Source` Simple / Advanced toggle on `M365 Agent`: `From Envelope` (default — reads the item's `conversationReference`) vs `Specify Manually` (structured fields for proactive sends that don't originate from an inbound activity).
- `M365 Agent Trigger` gains a `Response Mode` parameter (`Immediate` / `Wait For Response Node`) — the latter is required for invoke flows (`Action.Execute`, messaging-extension searches) where the bot must write a synchronous response.
- Codex metadata (`.node.json`) for both nodes — category: Communication.
- Adaptive Card rendering now surfaces parse / expansion failures as actionable `NodeOperationError`s with field name + item index, instead of leaking `SyntaxError` stack traces into the execution log.

**Removed**

- `M365SendActivity` → replaced by `M365 Agent` (resource: Message, operations: send / reply / update / delete / replyInThread).
- `M365TextMessage` → fold into `M365 Agent` (resource: Message, operation: send / reply / update, **Text** field).
- `M365CardTemplate` → fold into `M365 Agent` (resource: Card, operation: send).

**Changed**

- `usableAsTool` is OFF on both nodes. The `M365 Agent` node has side effects (writes to Azure Bot Service) and the Trigger is not an AI tool — letting an LLM autonomously invoke either isn't safe or useful.

**Migration**

1. Upgrade to 0.2.0.
2. In each workflow, delete any `M365SendActivity` / `M365TextMessage` / `M365CardTemplate` node and replace with a single `M365 Agent` node.
3. Pick the right Resource + Operation. Leave **Conversation Source** at `From Envelope` for replies / updates / deletes triggered by the inbound webhook; switch to `Specify Manually` for proactive sends.
4. Fill in **Text** (for Message ops) or **Card Template** + **Binding Data** (for Card/send).
5. Re-activate the workflow.

No automatic migration is provided — rebuild is manual. Existing envelope shape (`conversationReference`, `activity`, `parsed`, `raw`) is unchanged, so upstream logic that references those fields keeps working.
