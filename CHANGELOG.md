## 0.5.1 — 2026-04-20

### Fixed

- **Hero / Thumbnail card "Tap Action" no longer leaks phantom required-field errors** across the M365 Agent node. The shared `cardActionFields()` (Type / Title / Value, all `required: true`) was being consumed in two contexts: a `fixedCollection` of Buttons (correct — required fires only when a row is added) **and** a singular `collection`-wrapped Tap Action inside `Options` (the bug). n8n's frontend validator (`getParameterIssues` in `n8n-workflow/src/node-helpers.ts:1540`) walks every direct child of a `collection` unconditionally — no `isDisplayed` gate, no `value === undefined` guard. Because Type/Title/Value have no `displayOptions` of their own, the validator emitted `Parameter "Type" / "Title" / "Value" is required.` even on a fresh node, and even when the user had picked a totally different resource/operation (e.g. Message → Reply in Thread). Workflows could not be activated.

- **Fix:** wrap Tap Action in a singular `fixedCollection` (`multipleValues: false`) so the validator's fixedCollection branch — which DOES guard with `if (value === undefined) continue;` — skips the inner walk until the user opens "Add Tap Action". This is the n8n-core idiom for opt-in nested action groups (precedents: WhatsApp `Name`, Slack V1 Block Kit `Confirm/Title/Text/Accessory`, ActionNetwork `email_addresses` / `location`). `cardActionFields()` is unchanged — its `required: true` markers remain correct in the (already-fixedCollection) Buttons context.

### Changed (saved JSON shape)

- Tap Action saved shape changes from `options.tapAction = { type, title, value, ... }` to `options.tapAction.action = { type, title, value, ... }` on Hero / Thumbnail cards (both top-level `Options.tapAction` and per-image `images[].options.tapAction`). The wrapper `action` key is what the n8n validator uses as its `value === undefined` gate. **Not backwards-compatible** with manually-constructed 0.5.0 workflows that filled in Tap Action — re-add via the editor (or hand-edit the JSON to add the `action` wrapper). Editor-created cards on 0.5.1 work without intervention.

### Internal

- Fixed-collection wrapper is shared by `Options.tapAction` on Hero (`nodes/M365Agent/actions/card-hero/index.ts`), Thumbnail (`nodes/M365Agent/actions/card-thumbnail/index.ts`), and per-image `images[].options.tapAction` (`shared/cardBuilders/images.ts`). Builders updated to dereference `.action`: `shared/card/buildAttachment/hero.ts`, `shared/card/buildAttachment/thumbnail.ts`, `shared/cardBuilders/images.ts`. Tests updated in `tests/shared/cardBuilders/images.test.ts`, `tests/shared/card/buildAttachment/hero.test.ts`, `tests/shared/card/buildAttachment/thumbnail.test.ts`. Full investigation (with grep over n8n-core and citation of upstream precedents) at `docs/rkstack/brainstorm-notes/2026-04-20-n8n-collection-vs-fixedcollection-truth.md` in the parent workspace.

## 0.3.5 — 2026-04-19

**New**

- `Suggested Actions` Type dropdown now exposes **all 11 `CardAction.type` values defined by the M365 Agents SDK**: `call`, `downloadFile`, `imBack`, `messageBack`, `openApp`, `openUrl`, `playAudio`, `playVideo`, `postBack`, `showImage`, `signin`. Previously the node exposed only four (`imBack`, `messageBack`, `openUrl`, `postBack`) on the grounds that "four cover the 95% case for bot UX" — that framing scoped the node to a single internal test workflow. **Docs**

- `SuggestedActionInput.value` JSDoc updated to describe the payload semantics for every action type (tel: URI for `call`, app name for `openApp`, OAuth connection name for `signin`, etc.).

#### 0.2.1

**New**

- `M365 Agent` gains a `Card / Update` operation — re-renders an Adaptive Card in place by calling the Bot Connector's `updateActivity` with a new template expansion. Mirrors `Card / Send` (same Card Template + Binding Data + Fallback Text fields) but requires `activityId` on the conversation reference (the card to update). Closes the gap where state-changing Adaptive Card flows (e.g. status transitions with `Action.Submit`) had to chain a card build + raw HTTP call to update the original message.

Per manifest §6.1, `send` and `update` are variants of the same user intent on the `Card` resource — they live on one node, not two.

#### 0.2.0 — UX realignment (BREAKING)

The three separate action/builder nodes (`M365SendActivity`, `M365TextMessage`, `M365CardTemplate`) collapse into a single `M365 Agent` node using n8n-native resource/operation UX. Workflows saved against 0.1.x will not auto-migrate — they must be rebuilt on the new node shape.

**New**

- `M365 Agent` action node with resources `Message` / `Card` / `Invoke Response` and per-resource operations. Canvas subtitle shows `operation: resource`.
- `Conversation Source` Simple / Advanced toggle on `M365 Agent`: `From Envelope` (default — reads the item's `conversationReference`) vs `Specify Manually` (structured fields for proactive sends that don't originate from an inbound activity).
- `M365 Agent Trigger` gains a `Response Mode` parameter (`Immediate` / `Wait For Response Node`) — the latter is required for invoke flows (`Action.Execute`, messaging-extension searches) where the bot must write a synchronous response.
- Codex metadata (`.node.json`) for both nodes — category: Communication.
- Adaptive Card rendering now surfaces parse / expansion failures as actionable `NodeOperationError`s with field name + item index, instead of leaking `SyntaxError` stack traces into the execution log.

**Removed**

- `M365SendActivity` → replaced by `M365 Agent` (resource: Message, operations: send / reply / update / delete / replyInThread).
- `M365TextMessage` → fold into `M365 Agent` (resource: Message, operation: send / reply / update, **Text** field).
- `M365CardTemplate` → fold into `M365 Agent` (resource: Card, operation: send).

**Changed**

- `usableAsTool` is OFF on both nodes. The `M365 Agent` node has side effects (writes to Azure Bot Service) and the Trigger is not an AI tool — letting an LLM autonomously invoke either isn't safe or useful.

**Migration**

1. Upgrade to 0.2.0.
2. In each workflow, delete any `M365SendActivity` / `M365TextMessage` / `M365CardTemplate` node and replace with a single `M365 Agent` node.
3. Pick the right Resource + Operation. Leave **Conversation Source** at `From Envelope` for replies / updates / deletes triggered by the inbound webhook; switch to `Specify Manually` for proactive sends.
4. Fill in **Text** (for Message ops) or **Card Template** + **Binding Data** (for Card/send).
5. Re-activate the workflow.

No automatic migration is provided — rebuild is manual. Existing envelope shape (`conversationReference`, `activity`, `parsed`, `raw`) is unchanged, so upstream logic that references those fields keeps working.
